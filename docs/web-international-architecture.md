# 海外学生与家长 Web 技术选型

日期：2026-10-24。状态：React/TypeScript 双端已实施并上线；旧 Web 已下线。当前部署以 [部署与运维](deployment.md#6-google-play-海外双端-web) 为准，证据及剩余范围见 [Web 验收记录](web-acceptance.md)。

当前决策：品牌 **AI StudyNest**；官网 `https://aistudynest.com`、家长 `https://parents.aistudynest.com`、学生 `https://learn.aistudynest.com`。家长 Web 使用 Waffo 订阅收款并展示已核验权益；验单中继及通知已迁至官网，旧 `i.lix.do` 返回 410。真实 Google／模型／私有存储联调已完成记录范围，物理设备验收按用户“暂时不真机验收”延期。学生端支持同源资源访问，系统网站白名单仍须真机验证，网页不提供整机锁定。

以下第 1–9 节保留实施前的选型依据、当时现状和工时估算，其中“建议／需新增／未验证”是提案阶段描述，不是当前部署状态；其中历史结算候选不替代当前 Waffo 接入方案。

2026-10-27：海外 Web 收款改为 [Waffo](waffo-billing.md)，采用注册 3 天免绑卡与原生 30 天订阅试用。

## 1. 新的产品边界与结论

- 学生 Web 与家长 Web 均只面向非中国市场；从 Google Play 渠道官网进入，独立构建和部署。
- 国内官网移除 Web 入口，并停止提供旧 Web 页面；原生 App 的 API 不因下线页面而停止。
- 面向海外用户重新设计注册、家庭连接、语言、时间、订阅及浏览器交互，不只把中文 App 翻译成英文。
- iPad 与 Android 平板仍是学生端优先目标；家长端同时适配手机和桌面浏览器。
- 学生端保留单网站白名单能力，家长端允许其登录／付款必需的外部服务；两端分别配置。

推荐：**React + TypeScript + Vite + React Router，独立 Web 工程；保留 FastAPI 与 PostgreSQL，增加 Web 会话和海外业务适配。** 静态官网继续作为公开页面，学习应用独立构建。学生与家长共用源码模块，分入口构建、分源部署。

此前建议在 Python 字符串内增量扩展，适用于范围较小的学生聊天站。新增完整家长端、海外本地化和独立发布后，不再建议把双端逻辑继续堆进 `web_page.py`。

## 2. 已核实的现状

| 项目 | 当前实际状态 | 选型影响 |
|---|---|---|
| 官网 | `site/` 与 `site/googleplay/` 都是静态 HTML/CSS/JavaScript；海外首页 canonical 已按新品牌改为 `https://aistudynest.com/` | 没有现成 React/Vue 官网框架需要迁就；不必为了学习应用重写官网 |
| 国内入口 | `site/index.html` 链接 `/ai-zhuxue/`，正文和家庭步骤也提到 Web；API 提供 `/web` | 下线不能只移除按钮；还要核对反代旧别名和 API 页面路由 |
| 旧 Web | 单个 Python 字符串页面，学生聊天、老师、历史和文字收藏；无家长 Web | 新工程复用接口和行为参考，而不是复用原页面结构 |
| 家长 API | 家庭、孩子、绑定码、设备撤销、会话审查、反馈、搜索、收藏、成绩、评估、通知、订阅状态、注销申请等已有 | 前端不需要重建这些业务，但应补协议类型、分页／筛选和海外状态呈现 |
| Google 登录 | `/auth/guardian/google` 已支持 `googleplay`；服务端按 Google `sub` 关联家庭，校验 Web client ID audience | 优先接 Google Identity Services，可与现有 Play 账号关联；须配置真实网页 Origin 和受信任 client ID |
| 其他登录 | 普通用户没有自助邮箱注册；密码账号是预分配账号，学生密码登录仅限审核家庭 | 不能把现有密码入口视为海外自助注册已完成 |
| 日期与休息时段 | `local_time.py` 按固定 `TZ_OFFSET_HOURS`，默认 +8；约 10 个业务文件直接或间接使用该口径 | 海外多时区和夏令时是后端改造，不是浏览器格式化即可解决 |
| 订阅 | 有商店验单、通知和家庭权益；网页目录接口仍返回 CNY 配置价 | 不得把 CNY 数字换货币符号后当作海外成交价；Web 新购买须独立设计 |
| 角色与会话 | 目前用 Bearer token；家长登出会使该家长旧 token 失效；孩子只保留一个当前绑定设备 | Web 会话、退出范围和 App/Web 共存都要明确，不可默认独立多设备会话已存在 |

这些是仓库事实，不代表对应线上配置或购买路径已经验收。

## 3. 候选技术比较

| 方案 | 主要收益 | 本项目实际成本／限制 | 结论 |
|---|---|---|---|
| 继续原生 JavaScript 内嵌页 | 最快补少量学生聊天功能，无新前端构建 | 双角色、多页面、表单、国际化、缓存隔离和交互测试难维护 | 不作为双端正式方案 |
| Flutter Web | 可复用 Dart 业务与大量现有页面；官方支持现有移动应用的 Web 交付 | 仍需验证登录／支付插件、浏览器存储、图片、下载、文本选择、键盘与可访问性；海外用户体验要重新设计，不能只套移动页面 | 若团队坚持 Dart 单栈，可做验证；不是默认推荐 |
| React + TypeScript + Vite | 直接使用浏览器语义、表单、路由和响应式布局；可分端加载；静态产物独立部署 | 新增一套 UI 代码；需维护与 Flutter 的接口／行为一致性 | **推荐** |
| Vue + TypeScript + Vite | 同样适合后台与学习应用，部署成本接近 React | 同样需要重写 Web UI；本仓库未显示现有 Vue 资产 | 若实际维护团队更熟 Vue，可等价替换；无需为 React 额外培训 |
| Next.js | 公开内容、服务端渲染、预渲染、登录应用可在同一框架组织；也支持静态导出 | 当前已有静态官网和 FastAPI；登录后应用缺少必须 SSR 的理由，完整服务端模式会多一套运行服务 | 当前不优先；未来大量多语公开内容／SEO 页面再评估 |

React 官方偏向从框架开始，同时说明框架可采用纯客户端和静态部署；因此不应把“Next.js 一定要 Node 服务”作为拒绝理由。本建议选择 Vite 的依据是现有 FastAPI 和静态官网已分工明确，登录后应用不需要服务端页面渲染。

Flutter Web 技术可行，不能用“不支持 iPad”或“不适合任何网页”否定。是否省总工期需要真实原型；本次未构建 Flutter Web，也未测首屏，不能声称它一定更慢或一定更省。

## 4. 推荐的工程与部署组织

建议新增 `product/web/`，一个 package 与锁文件，学生／家长两个构建入口，按路由懒加载页面。共享 UI 基础、语义化翻译键、API 类型、附件展示和日期格式化；不共享授权状态或私有数据缓存。首期不引入 monorepo 管理工具或独立 Node 业务后端。

最小技术组合：

- React + TypeScript：页面、组件和类型。
- Vite + React Router：构建、分包、路由、浏览器返回和可分享页面地址。
- i18next／react-i18next + 原生 Intl：翻译、复数、日期、数字、货币与语言回退。
- React Query 可用于家长大量列表／详情与失效刷新；聊天流保持专门状态，不把增量消息当普通轮询列表。若采用路由数据能力足够，先不重复引入。
- CSS variables／CSS Modules 和少量可访问组件；不为赶后台表格把整个学生端套成管理后台。
- 沿用项目的 Markdown 消毒与公式能力并固定版本；字体、脚本均随构建产物同源提供。
- Playwright 覆盖核心浏览器流程；现有 pytest 继续覆盖权限、时区、设备、订阅和图片逻辑。自动化 WebKit 不替代真实 iPad。

部署关系：

```text
Google Play 渠道官网（现有静态站）
  ├─ 家长入口 → 家长 Web 静态产物 → 本源 /api → FastAPI
  └─ 学生入口 → 学生 Web 静态产物 → 本源 /api → FastAPI
                                                   ├─ PostgreSQL / 家庭权益
                                                   ├─ 私有图片存储和审核
                                                   └─ 模型服务
```

学生／家长已采用两个子域名，属于 AI StudyNest 同一官网产品，具体域名见本文开头；服务器以私有生产说明及实际运行配置为准。分源使学生学习页与家长登录凭据隔离，也便于学生白名单只允许学习域名。若必须用一个主机的两个路径也能实现，但不具备独立源隔离，需接受这一取舍。

两个静态产物都可由 Caddy/Nginx/CDN 提供；Node 仅用于构建。各自 `/api` 由网关转发到批准的 API，避免浏览器常态跨源请求。新 Web 会话适配在 FastAPI 实现，不另加一层 Node BFF；原生 App 继续使用原 Bearer API。

“前端单独部署”不等于“数据库必须复制”。优先复用已确认的海外／Google Play 后端和账号数据；若当前实际上只有共享后端，则先在其上做明确渠道与 Web 接入隔离。不要为了官网部署另起空数据库而导致已有 Play 用户失去家庭／订阅。服务器是否迁出中国、模型／图片区域是否调整，是独立基础设施决策，需实测目标地区延迟。

## 5. 海外用户体验与后端必须补的能力

### 5.1 语言和信息结构

初次按浏览器支持语言选择，未支持语言回退英文，并可手动切换。英文作为完整的基准文案；保留现有七语对照，但由母语或熟悉目标市场的人复核。海外中文用户仍可选中文，语言不作为地区授权依据。

使用明确的 Parent、Student、Child profile、Learning activity 等文案；家长登录后按创建孩子、设置家庭时区／使用计划、连接学习设备的步骤引导。孩子先知道家长可查看哪些记录，再开始学习，不让孩子必须拥有 Google 账号。

成绩先沿用已有“得分／满分”和自定义科目，不假设各国都是百分制，也不把年龄段直接翻译成某国学年。字母等级、GPA、国家课程体系如要支持，单独扩展数据模型。

家长端采用桌面侧栏、孩子切换和清楚的设置分组；手机退为单列。学生端聚焦对话、附件和学习反馈，保留平板分屏、触屏和键盘操作。所有交互状态和无障碍标签都进入翻译资源，不扫描中文 DOM 文本作为新应用的翻译键。

### 5.2 时区、日期与夏令时

新增家庭 IANA 时区，例如 `America/New_York`；浏览器只建议默认值，由家长确认。数据库时间戳保持 UTC，服务端用 `zoneinfo` 计算该家庭的学习日期、休息时间、每日额度、奖励、摘要、成绩筛选和统计边界。

不能把全局 +8 改成另一个固定偏移，也不能只把页面显示改成本地时间。冬夏令时导致一天不总是 24 小时，应分别计算本地两次午夜后转换为 UTC。当地重复／不存在的时刻和切换家庭时区后的计数策略要有测试和明确规则。

现有 ActiveTime 等按日期累计的数据不能简单重新命名日期：老记录保留其历史口径，按确定的切换时点开始新口径，避免凭空移动已用额度。国内家庭没有新配置时保持旧逻辑，现有 App 请求保持兼容；海外 App 若显示同一家庭数据，也需要最小兼容验证。

### 5.3 登录与角色安全

家长首期用 Google Identity Services 接现有 Google 家庭标识。配置 Web OAuth client、允许的 Origin 和回调；服务端验证 ID token 的 audience、issuer、签名和有效期，用 `sub` 关联用户。需要增加 Web client ID 时，只加受信任的明确列表，不取消 audience 检查。

非 Google 用户的自助邮箱验证码／登录链接值得后续支持，但当前不是现成能力：需要邮件投递、限流、凭据恢复和账号关联，不要把预分配密码登录宣传成自由注册。学生继续用家长生成的一次性连接码；同设备切换到学生页也必须显式确认，不通过 URL 携带长期 token。

家长高权限 Web 不建议照搬旧 Web 的 localStorage 长期 Bearer。FastAPI 增加角色独立的 Web session，用 Secure、HttpOnly、host-only cookie，并实现服务端校验的 CSRF／Origin 防护、过期、撤销。两端会话和缓存独立；cookie 的 SameSite 不能替代 CSRF，分子域也不能替代后端角色检查。

新 Web session 需明确“退出当前浏览器”和“退出所有设备”语义，不能直接照搬现有登出使所有该家长 token 失效的行为而不提示。孩子多设备并存目前没有支持，首期可保留单设备并明确告知；如果希望 App＋Web 并存，必须连同唯一索引、绑定、吊销与计时一起改。

### 5.4 订阅与支付

Google Play 渠道官网是发布归属，不等于浏览器可以使用 Android 原生 Play Billing。Google Pay Web 也是另一种支付 API，不能当作商店订阅恢复接口。

两个交付级别：

1. **已有 Play 家庭的伴随 Web**：网页显示已核验权益、使用学习和管理功能，订阅管理指向原购买平台；不在网页产生新扣款。最快落地，但只有 iPad／电脑的新家庭无法单靠它完成付费，必须如实说明。
2. **可独立获客的完整 Web**：增加网站订阅结算。支付商在确认运营主体、支持地区与结算币种后选择；可优先评估托管 Checkout＋订阅管理门户，降低自行处理支付表单的工作。服务器处理签名 webhook、幂等、取消／退款、权益到期和跨来源重复订阅，不凭支付成功跳转直接发权益。

推荐首期工程上先复用 Play 权益跑通双端；若目标包括“没有 Android 的家长也能注册并付费”，网站结算应作为正式商业发布门槛。展示 Web 本地币种价格不能读取当前固定 CNY 的目录后换符号；商店购买则以商店确认价格和状态为准。

数据模型把市场（international）、客户端（web/android/ios）和付款来源（googleplay/web provider）分开。Web 老师目录初期与 Google Play 保持一致，但不把 Web 付款伪装成 Google Play 验单，也不在 Flutter 中新建一套相同家庭权益。App 内引导网页支付的政策问题不纳入本方案默认行为，需按实际渠道和地区另核对。

## 6. 白名单与地区边界

学生入口只加载本站资源，并通过本源受控媒体上传／读取访问私有图片；严格白名单不向浏览器暴露必须访问的存储／模型域名。所有数学字体和渲染资源打入本地产物，限制外链、外部图片和外部 App 协议。

家长 Google 登录需要 Google 官方脚本和登录服务，不能将其 SDK 随意复制成本地脚本来满足单域名。家长支付也需要付款服务。把学生和家长分源，可让孩子只放行学习站，而不必放行 Google 登录与支付站点。学生所需隐私／帮助说明应在学习域名有可访问内容，不强迫打开家长站。

“非中国市场”由服务配置和入口发布策略表达，不能靠中文／英文或 `X-App-Channel` 判断用户位置。该请求头可被客户端修改，只能用于路由选择，不能作为安全边界。如要求强制限制中国地区访问，需要在 Web 边缘或服务端做地区判定，先明确地区口径；不要把地理 IP 识别宣称为国籍或居住地验证。此限制只作用于 Web，不顺带封禁原生 App 必需接口和支付回调。

## 7. 国内旧 Web 下线方案

实施时同时覆盖：

1. `site/index.html` 的 `/ai-zhuxue/` 按钮、功能介绍、家庭连接步骤；同步国内翻译资源，检查国内隐私／条款中的现行产品范围。
2. 国内站反代 `/ai-zhuxue/` 等旧别名，直接访问旧链接也应返回明确的下线结果（可用 410 页面）；不自动跨境带 token 跳转海外站。
3. API 的旧 `/web` HTML 路由：新海外应用稳定后停止提供，或在过渡期按部署配置明确关闭国内入口。更新 Web 页面测试和 API 文档，必要时移除旧内嵌页。
4. 不删除 App 使用的 `/chat`、`/auth`、`/parent` 等业务接口。确认静态 CDN／反代缓存，提供回滚页面配置。

新海外站增加独立家长／学生入口。现有 `site/googleplay` 路径只是仓库目录，不代表生产 URL 必须有 `/googleplay/` 前缀。当前 canonical 提供地址线索，但实际部署、代理和回调参数仍须按最新生产配置核实。

当前轮只评估；没有修改官网 HTML、反代或 API 路由，没有执行生产下线。

## 8. 工作量与落地顺序

相较上一份学生端评估，新范围增加了家长 Web、独立工程、浏览器安全会话和家庭时区。不能沿用 22–32 人日作为整个项目预算。

基线假设：熟悉项目的全栈工程师；首期七语资源结构与现有翻译复用，英文重点验收；复用当前后端和 Play 权益；严格学生单域名；不新增支付商、自助邮件账号、多监护人邀请或孩子多设备并存。

| 工作包 | 内容 | 基础人日 |
|---|---|---:|
| Web 工程与双端会话 | React/TS、分入口构建、共享基础、Google 登录、独立 Web session／CSRF／角色缓存 | 7–10 |
| 学生主流程 | 平板、绑定、SSE、会话、图片输入输出、收藏、限制及计时；吸收前版分析 | 16–23 |
| 家长主流程 | 家庭与孩子、连接／重绑／撤销、会话审查、使用设置、通知、已有订阅状态和管理入口 | 12–18 |
| 海外业务改造 | 家庭时区、夏令时／日界、迁移兼容、错误与文案、语言／日期／价格呈现 | 8–12 |
| 联调与发布准备 | iPad／Android／桌面、严格白名单、权限回归、独立部署配置／回滚、国内入口下线准备 | 6–9 |
| **可用双端合计** | **核心学习与家长管理，复用 Play 权益** | **49–72** |

加约 20% 工程风险余量后约 **59–87 人日**；一名工程师约 12–18 个工作周。可先上线仅给现有 Play 家庭使用的版本，再补独立购买。前后端两人可并行，但时区、会话、验单和真机依赖使工期不能简单减半。

主要增量（基础人日，若加入范围再统一计算余量，不能重复计算）：

- 学生学习反馈／奖励、完整成绩评估、家长完整成绩／评估／导出等长尾页面：8–14 人日。核心版未承诺两端逐项全量对齐 App。
- 网站独立订阅：10–16 人日，含托管结算、webhook、权益与管理；不含支付商开户审核／税务配置等待。
- 自助邮箱登录与可靠关联／恢复：4–7 人日，不含邮件服务开通与投递信誉爬坡。
- 孩子 App/Web 多设备并存：4–7 人日，含绑定／撤销和使用时长规则；若保留单设备不投入。
- 从共享后端拆成海外数据库、账号／权益迁移、存储区域迁移：须另勘测，不能按“前端上传官网”估算。

推荐顺序：

1. 做 3–5 人日关键验证（已包含在上表，不额外累加）：家长 Google Web 登录关联原家庭；iPad SSE／键盘＋单域图片；IANA 时区对额度／奖励／摘要的影响。验证结果后收敛正式排期。
2. 完成共享底座和家长创建／连接流程，再接学生文字及图片；时区和角色校验作为首版底座。
3. 接入家长核心管理与 Play 权益，完成目标市场／设备联调，部署海外入口并同步国内旧 Web 下线。
4. 按独立获客目标决定是否把网站订阅并入首发；其余页面逐步补齐。

## 9. 官方依据与未验证边界

- [React：创建应用](https://react.dev/learn/creating-a-react-app)：框架、CSR／SSG 与可静态部署的能力。
- [Vite：静态部署](https://vite.dev/guide/static-deploy.html)：构建产物可部署到静态主机；preview 不用于生产服务。
- [React Router：SPA](https://reactrouter.com/how-to/spa)：客户端路由和静态交付能力。
- [Next.js：静态导出](https://nextjs.org/docs/app/guides/static-exports)：Next.js 并非必须运行 Node 服务器。
- [Flutter：Web FAQ](https://docs.flutter.dev/platform-integration/web/faq)：现有 Flutter App、SPA 可用，公开文档型页面的适用边界不同。
- [Google：Web 登录配置](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid)、[ID token 验证](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)：Origin、client ID、受信任 audience 与 `sub`。
- [Python：zoneinfo](https://docs.python.org/3/library/zoneinfo.html)：IANA 时区与夏令时处理。
- [MDN：Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)：HttpOnly、Secure、Domain 等浏览器会话机制。
- [Google Play Billing 集成](https://developer.android.com/google/play/billing/integrate)、[Google Pay Web](https://developers.google.com/pay/api/web/overview)：原生商店结算与网页支付 API 的不同角色。
- [Stripe：订阅集成选项](https://docs.stripe.com/billing/subscriptions/build-subscriptions?payment-ui=checkout&ui=stripe-hosted)：托管结算是网站支付候选，不表示已核实本项目开户资格。
